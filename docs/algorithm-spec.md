# 调度算法规范

## Stage 1 配置

Stage 1 固定应用提交顺序为递增记录 ID，只有一个固定负载和一个应用并发上限。传输层使用固定版本的上游 `xqc_minrtt_scheduler_cb`。该实现跳过未激活或冻结的路径，检查拥塞窗口，再按路径性能类别与平滑 RTT 选择可发送路径。两个阶段使用相同的调度器、CUBIC 和 pacing 设置。

| 参数 | 含义及单位 | Stage 1 取值 | 调整方式 |
| --- | --- | --- | --- |
| `RECORDS` | 每批记录数，正整数 | 64 | 调整固定负载规模 |
| `RECORD_BYTES` | 每条记录的线上应用字节数，大于 4 | 16,384 | 调整每个 Stream 的数据量 |
| `TX_WINDOW` | 尚未收到 Stream 关闭通知的本端发送 Stream 上限，正整数 | 16 | 固定并发条件或测试负载压力 |
| `max_streams_uni` | 本端向对端提供的初始单向 Stream 累计 credit，正整数 | 32 | 用较小值验证 XQUIC 的 credit 补充 |
| `init_max_path_id` | 初始允许的最大路径 ID，0 使用上游默认值 | 1 | 给初始路径 0 和新增路径预留空间 |

路径 B 的观测占比为

```text
B_SHARE = Δ B_data_rx_bytes / (Δ A_data_rx_bytes + Δ B_data_rx_bytes)
```

每个差值取相邻批次完成快照的累计计数差，首批的起始应用数据计数为零。占比是包级观测指标，可能计入重传和协议开销。批完成时间以客户端批开始到服务端记录 `phase_complete` 的单调时钟差计算，客户端 ACK 耗时另计。

## Stage 2 提交规则

Stage 2 按待发记录的输入顺序提交，并允许同传感器状态在队列内做最新值替换。优先级、严重程度、截止时间和最大年龄作为记录元数据。过期记录仍有资格提交，接收端用完整接收时间独立判定截止。记录格式、时间口径和流控参数见 [Stage 2 技术报告](stage2-report.md)。

## Stage 3 应用调度基线

每次提交前，Gateway 在已释放的待发记录中选一条。成功创建单向 Stream 后才移出队列并提交轮转状态。建流遇到 credit 限制时，下一次按届时的队列和 ACK 快照重新选取。五种策略均保留过期记录的提交资格。

| 策略 | 选取规则 | 待发状态替换 |
| --- | --- | --- |
| `fifo` | 最早输入。 | 关闭 |
| `strict-priority` | `priority` 最大；并列按输入顺序。 | 关闭 |
| `edf` | 绝对 deadline 最早；并列按输入顺序。 | 关闭 |
| `aoi` | 归一化潜在 AoI 改善最大；并列按输入顺序。 | 关闭 |
| `latest-rr` | 两类都有待发记录时交替服务状态和事件，初始先服务状态。事件内部 FIFO，状态按传感器 ID 升序循环，从上次成功提交的传感器之后继续；仅一类可用时直接服务该类。 | 启用 |

AoI-aware 对已知传感器的候选状态计算

```text
score = max(0, generated_us - latest_acked_generated_us) / maximum_age_us
```

`latest_acked_generated_us` 是客户端已经收到的该传感器 ACK 快照中的最大生成时间。候选状态的生成时间和反馈统一用相对重放原点的微秒。`maximum_age_us` 是正数，单位为微秒，尺度较小的传感器在同等新鲜度增益下得分更高。该比值无量纲，范围从零到非负无上限。每次得分使用当时可见的 ACK，旧 ACK 到达时不会回退估计。尚无 ACK 快照的状态得分为 1，事件得分为 0。该策略只比较新鲜度收益，没有额外的严重程度或防饥饿项。

## Stage 4 联合规则

Stage 4 使用以下可解释规则作为研究原型。调度发生在有应用槽位且尝试取得单向 Stream credit 时。失败的建流不改变计数和队列，成功后绑定 Stream 的初始路径。待发状态仍按传感器替换，并丢弃已收到 ACK 证明其版本不比接收端更新的记录。事件独立保留。

设 `t` 为决策时刻，`g` 为生成时刻，`a` 为释放时刻，`d` 为绝对截止时间，`M` 为状态的最大年龄，`u` 为客户端已知的最新生成时间。所有时间使用同一单调时钟，以下公式采用微秒。状态剩余预算 `s = min(d - t, M - (t - g))`，事件预算 `s = d - t`。`s <= 0` 的状态进入恢复类。是否还有更新价值使用 `(g, sequence_id)` 与 ACK 快照比较。

### 路径估计

```text
T = (0.5 + 2 · [PTO > 0]) · SRTT + 10^6 · (Q + B) / max(rate, 15000)
σ = max(RTTVAR, 1000)
L = min(0.95, (recent_lost + 1) / (recent_sent + 20))
P = 0                                                       if s <= 0
P = clip((s - T + σ) / (2σ), 0, 1) · (1 - L)^ceil(B/1200)     otherwise
```

路径候选须已激活且未冻结。先最大化 `P`，并列取较小的 `T`，仍并列保留 XQUIC 路径遍历顺序。该概率是延迟均匀窗口与独立丢包假设下的启发式，未作统计校准，且未把重传成功计入。路径初始分配按整条记录估计，备用路径的重传决策按单包重新估计。

| 参数 | 含义、单位及范围 | 默认值与作用 |
| --- | --- | --- |
| `SRTT`、`RTTVAR` | 路径平滑 RTT 与 RTT 波动，µs，非负 | XQUIC 实测，决定传播项及延迟区间 |
| `PTO` | 未恢复的 PTO 次数，非负整数 | 非零时增加 2 个 SRTT 的估计惩罚 |
| `Q`、`B` | 该路径在途加已调度字节、当前待发字节，非负 | `B` 包含应用头；修复时使用 QUIC 包当前大小 |
| `rate` | 路径带宽估计，字节/秒，非负 | CUBIC 下由 XQUIC 用拥塞窗口与 SRTT 估计，分母下限 15,000 |
| `recent_lost`、`recent_sent` | XQUIC 当前和上一近期窗口的包计数 | 加 1/20 作为冷启动平滑，`L` 截于 0.95 |
| `σ`、分段尺度 | µs 与字节，正数 | 波动下限 1,000 µs，分段 1,200 字节 |

### 队列评分和公平性

令 `sat(x)=x/(1+x)`，等待项 `W=sat((t-a)/H)`，`H=100000 µs`。优先级及严重程度为 0–255 的字段值并经 `sat` 归一化。状态改善项 `G=sat((g-u)/M)`，超龄项 `X=sat(max(0,(t-u)/M-1))`。没有状态 ACK 时取 `G=X=1`，事件取 `G=X=0`。非恢复候选与恢复候选分别评分。

```text
正常状态或事件   sat(priority) + 2·sat(severity) + G + W + P·(1 + H/(H+max(0,s)))
过期状态恢复     sat(priority) + G + X + W
```

默认严重程度权重为 2，其他加项权重为 1。事件即使过期仍保留优先级、严重程度和等待项。过期状态的所有路径估计 `P=0`，恢复类仍按第二个分数选取。分数并列按输入顺序。先执行 K 次普通状态机会约束，再执行连续事件约束，其余时候比较正常状态和事件的分数。只有恢复类可发时直接恢复。

| 参数 | 含义及范围 | 默认值与选参 |
| --- | --- | --- |
| `K` | 两次恢复之间累计的普通状态成功提交机会阈值，整数 1–64 | 默认 2，达到后下一次有恢复候选即优先恢复；恢复后归零。脚本可设 `IOT_RECOVERY_K` |
| `E` | 有状态待发时允许连续提交的事件数上限，正整数 | 当前 3，状态成功提交后归零 |
| `H` 与权重 | 等待和紧迫度的尺度（µs），各归一化项的无量纲系数 | 较小 `H` 提前放大等待。默认值用于当前受控验证，后续用不同负载和种子扫描 |

配额计数针对成功提交的机会。credit 耗尽、链路停滞或 Stream 前序字节缺失都会影响实际交付时间。K 可用 1、2 等值做成对复现，其他模型常数、事件配额及权重适合在 Stage 5 的可控场景中单独校准。

### 路径亲和

- `proposed-strict` 将客户端数据 Stream 的初发、普通重传和含 STREAM 帧的 PTO 副本固定在初始路径。
- `proposed-cross` 保留初发亲和性。对修复副本，若原路径不可用、拥塞窗口阻塞、进入 PTO 或预计完成时间达到剩余预算，允许选择满足备用路径拥塞窗口的候选。原路径进入 PTO 时优先尝试尚无 PTO 的备用路径，其余比较 `P` 与 `T`。
- 控制帧和服务端 ACK Stream 沿用上游调度。接收端依旧等待同一 Stream 的前序字节与 FIN。跨路发送可能改变字节到达顺序，接收端只有完整交付后才计成功。
