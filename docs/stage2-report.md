# Stage 2 技术报告

## 数据与协议

Python 生成器输出带 seed 的周期传感器状态和集中事件。负载文件按释放时间排序，每个条目前缀包含大端 `release_us: u64` 和记录长度 `u32`。生成时间、截止时间与释放时间在负载文件中均为相对微秒。客户端在确认两条 QUIC 路径可用后建立重放时钟原点，并将线上生成时间和截止时间转换为同机 `CLOCK_MONOTONIC` 绝对微秒。生成时间来自输入计划，实际入队、提交、完整接收和 ACK 到达由运行日志分别记录。

ALPN 为 `iot-stage2`。所有整数采用网络字节序，一个单向 Stream 承载一条数据或一条 ACK，以 FIN 确定记录完整。数据头固定 52 字节，payload 最大 16,384 字节，单连接最多重放 1,024 条记录。

| 偏移 | 宽度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | 版本标记 `IOT1` |
| 4 | 1 × 4 | 类型（1 状态、2 事件）、优先级、严重程度、保留位 |
| 8 | 4 | payload 字节数 |
| 12 | 4 | 本次重放的唯一记录 ID |
| 16 | 4 | 状态的 `sensor_id` 或事件的 `event_type` |
| 20 | 8 | 状态的 `sequence_id` 或独立的 `event_id` |
| 28 | 8 | 生成时间（µs） |
| 36 | 8 | 截止时间（µs） |
| 44 | 8 | 最大信息年龄（µs），事件为 0 |
| 52 | 可变 | payload |

ACK 固定 44 字节，前 8 字节为 `IOT1`、类型 3、结果、截止标志及保留位。随后依次为记录 ID（4 字节）、原数据 Stream ID、服务端完整接收时间、当前传感器最新生成时间和序号（各 8 字节）。结果 1 为状态更新，2 为过旧状态，3 为接受事件，4 为重复事件。事件 ACK 的两个状态快照字段为 0。

## 队列和接收规则

- 每个传感器最多保留一条待发状态。按 `(generated_time, sequence_id)` 比较，保留较新的记录。成功创建 Stream 后记录进入已提交状态，发送缓冲持有该记录的完整编码。后续同传感器记录可以入队，已提交记录继续发送原内容。
- 每次事件输入独立占一个待发条目。接收端按 `event_id` 幂等处理，同一事件 ID 的再次交付仍返回独立的记录级 ACK。状态接收端保留各传感器的最新时间戳、序号和 payload。
- 当前按待发输入顺序提交。优先级和严重程度随记录传输，供后续算法使用。过期记录仍可提交，并记录提交过期标志、接收时信息年龄是否超限，以及是否在服务端按时收到 FIN。事件 ACK 返回结果与接收时间。
- 每端应用发送 Stream 并发上限为 8，只有 `stream_close_notify` 释放槽位。对端初始单向 Stream credit 为 4，由 XQUIC 通过 `MAX_STREAMS` 更新。建流失败保留原待发条目，并以 5–50 ms 退避重试。发送缓冲限制为 24 个包，用于触发部分写与 `EAGAIN`。正返回值推进偏移，`EAGAIN` 保留偏移，写回调续传。

## 复现

```bash
bash scripts/build.sh
sudo bash scripts/run-stage2.sh
python3 evaluation/verify_stage2.py RESULTS_DIRECTORY
```

验收器从保存的二进制输入重建待发队列，按日志顺序检查实际替换和提交。它逐条核对完整记录的元数据和 payload 校验值、双向 FIN 和关闭、服务端状态快照、ACK 匹配与时间、credit 和窗口恢复，并交叉检查两张 veth 的抓包与 XQUIC 帧日志。

## 实测结果

2026-11-07 在 Ubuntu 24.04 WSL2 用 seed 17 独立运行两次。两次输入文件逐字节一致。两端各验证两条可用路径，服务端从 A 收到 306 个携带 STREAM 帧的包，从 B 收到 10 个，两张网卡的抓包均报告零内核丢包。

| 检查项 | 复跑 1 | 复跑 2 |
| --- | ---: | ---: |
| 输入记录 | 56 | 56 |
| 待发状态替换 | 28 | 28 |
| 已提交并收到 ACK | 28 | 28 |
| 更新 / 过旧状态 | 6 / 1 | 6 / 1 |
| 接受 / 去重事件 | 20 / 1 | 20 / 1 |
| 服务端截止违约 | 8 | 8 |
| 客户端峰值活动发送 Stream | 8 | 8 |
| 客户端收到的 `MAX_STREAMS` 包 | 21 | 22 |
| 客户端部分写 / `EAGAIN` | 17 / 3 | 18 / 3 |

重放故意包含短截止记录和重复事件，发送缓冲也刻意设小。表中的违约次数用于检验记录与判定逻辑。调度算法的对照和时效性评估留到后续阶段。
