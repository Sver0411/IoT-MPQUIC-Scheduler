# ACK 驱动的路径时延校正

六个真实 XQUIC 配对中，ACK-Adaptive Probability 没有改变选路或事件按时率。反转后 A 路出现了可学习的正残差，但反馈晚于主要提交窗口。保留 `IOT_PATH_POLICY=ack-adaptive` 作为 Proposed-App 的可选策略。

## 实现

每个成功提交的 Stream 保留初始绑定路径、未校正的交付耗时预测和提交时间。客户端验证应用 ACK 后，以服务端完成应用交付的单调时间减去客户端提交时间，得到实际交付耗时。两端在同一个 WSL2 内核的网络命名空间中运行，使用同一个 `CLOCK_MONOTONIC` 时间基准。传输层 ACK 不参与学习。

每条路径独立累积 `实际交付耗时 − 原始预测耗时`，用 `0.25 × 残差 + 0.75 × 上一次偏差` 更新 EWMA。从零起步，在第 3、4、5 个有效 ACK 后分别应用正偏差的 1/3、2/3 和全量。负偏差的校正量为零。校正后的耗时进入原有按时概率计算，保留 RTTVAR 和丢包计算。应用 ACK 到达前的决策只使用此前已经累积的反馈。独立 Oracle 从记录、路径快照和 ACK 重放选路及更新。

## 真实 XQUIC 对照

WSL2 Ubuntu 24.04。沿用已有工程反转 `c93-002` 和 Client A 中断 `c93-000`，均为高负载。每个场景使用 `3942000`、`3942001`、`3942002` 三个配对种子。配对内工作负载 SHA-256、网络种子、配置、构建和 Proposed-App 严格路径绑定一致。以固定种子随机化两策略的运行顺序。沿用 E0 的 QUIC 抓包，用 netlink 配置完成时间对齐切换阶段。

| 指标 | A→B 反转，原策略 → ACK 自适应 | Client A 中断，原策略 → ACK 自适应 |
| --- | ---: | ---: |
| 事件按时交付率 | 6.52% → 6.52% | 4.05% → 4.05% |
| 有效 Goodput（kbit/s） | 73.58 → 72.58 | 82.00 → 82.00 |
| 已观测平均状态 AoI（ms） | 753.27 → 756.93 | 539.92 → 541.29 |
| 状态 AoI 覆盖率 | 93.07% → 93.10% | 93.04% → 93.06% |
| 最大年龄违约率（全窗口） | 99.86% → 99.83% | 99.89% → 99.87% |
| 下行 UDP 流量 A / B | 92.34% / 7.66% → 92.08% / 7.92% | 95.91% / 4.09% → 95.90% / 4.10% |

| 场景 | 种子 | 按时事件（两策略相同） | Goodput 差（kbit/s） | 平均 AoI 差（ms） |
| --- | ---: | ---: | ---: | ---: |
| A→B | 3942000 | 3 / 46 | −3.00 | +3.43 |
| A→B | 3942001 | 3 / 46 | 0.00 | −3.69 |
| A→B | 3942002 | 3 / 46 | 0.00 | +11.22 |
| Client A 中断 | 3942000 | 3 / 74 | 0.00 | −0.23 |

| Client A 中断 | 3942002 | 3 / 74 | 0.00 | +0.92 |

差值为 ACK 自适应减原策略。下行 UDP 流量包含协议和控制报文。两策略在所有种子都把应用 Stream 绑定到 A，每个反转运行共 62 次，每个中断运行共 72 次。B 无应用交付反馈，残差未知。对自适应策略逐条使用相同候选快照重算原策略，选路改变数为零。

## 反馈为何没有改变决策

- **反转。** 自适应策略的 A 路平均残差从反转前提交的 −0.99 ms 变为反转后提交的 +12.04 ms，每个种子分别有 24 条和 12 条可用 ACK。校正前后的已 ACK 样本绝对误差均值在两阶段分别同为 0.99 ms 和 12.04 ms。首次反转后选路时，A 的 SRTT 为 8.42–8.82 ms，B 的约 90 ms SRTT 已约 0.99 s 未更新。反转后提交的记录从服务端交付到客户端收到应用 ACK，各种子的中位数为 0.93–0.96 s。EWMA 首次转正距 netlink 切换完成约 1.28–1.31 s，只有两个种子在后续决策中实际使用了正校正。运行末 A 的偏差为 7.05–7.66 ms，样本不足以确认收敛。
- **中断。** 配置中断窗口内没有新的应用 Stream 提交。自适应 A 路中断前后的平均残差分别为 −0.81 ms 和 −0.29 ms，各种子分别有 24 条和 12 条可用 ACK，始终未施加正校正。恢复后的首次提交比 netlink 恢复完成晚 109–122 ms。

这批配对没有显示上线收益。调整 EWMA 系数无法补齐 B 路缺失的交付反馈，也无法为中断窗口补出选路机会。下一步可用现有随机路径探索测量两条路径在切换附近的 ACK 覆盖和反馈时延，再判断是否值得改进在线校正。

## 复现与证据

在现有 WSL2 工程环境中使用与 `scripts/build.sh` 一致的构建目录和已有实验 Python 环境。

```bash
sudo env OPENBLAS_NUM_THREADS=1 /path/to/venv/bin/python -B \
  experiments/run_ack_adaptive.py /tmp/iot-ack-adaptive --build /path/to/build
```

12 次运行均通过独立 Oracle，从本地归档重新核对全部文件 SHA-256 并复算指标。现有测试命令通过 50 项检查。第一次运行在汇总阶段因读取错误的路径计数字段而失败，原始日志和抓包一并保留。修正解析后重跑了完整配对，本报告使用这 12 次运行。

本地归档位于 `results/runs/ack-adaptive/paired-xquic.tar.gz`。SHA-256 为 `08919509d6a949517dc20f49baf4ba5467060775fef8b69ea1d48691bbb70873`。
